## Выбранная LLM и исследованные материалы

Основной checkpoint для **реального дообучения**: **`Qwen/Qwen3-4B-Instruct-2507`**, ревизия `cdbee75f17c01a7cc42f958dc650907174af0554`, Apache-2.0, локальные открытые веса, non-thinking. [Официальная карточка](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507), [PEFT QLoRA](https://huggingface.co/docs/peft/developer_guides/quantization), [TRL SFTTrainer](https://huggingface.co/docs/trl/sft_trainer). Для GPU 8 ГБ резерв — Qwen3-1.7B; для основной 4B-ветки предпочесть машину с 16 ГБ и короткий контекст.

Новое обязательное требование пользователя: выполнить **SFT через QLoRA**, сохранив zero-shot/few-shot как исходные контрольные прогоны. Раздел 6 общей подборки содержит формат данных, стартовый конфиг, проверки loss mask, адаптера и загрузки. Обучение выбранной LLM ещё не выполнено; твой агент должен реализовать и запустить его на данных команды.

Версия 3. Твой собственный подход — **LLM в zero-shot, few-shot и SFT/QLoRA режимах**. Кроме него ты отвечаешь за общий запуск четырёх извлекателей, минимальную демонстрацию и комплект сдачи. Rules делает № 1, CRF-NER — № 2, дообученный трансформер — № 3. Не бери на себя обучение их моделей: каждый владелец передаёт готовый адаптер, артефакты и отчёт.

## Задачи по порядку

### 1. Каркас и доступность LLM

В первые 10% времени создай устанавливаемый пакет `catalog_ai`, конфиги, CLI и интерфейсы-заглушки. № 1 передаёт contracts/fixtures, № 2 — normalizer/validator, № 3 — resolver. Проведи синтетическую карточку через каждый режим для проверки совместимости; отсутствие настоящей модели показывается как явный незавершённый режим, а не как успешный эксперимент.

Проверь доступный LLM-провайдер или локальную instruction-модель, бюджет и условия отправки датасета во внешний API. Ключи — вне репозитория. Если API недоступен/не разрешён, проверь локальную LLM; эта ветка не заменяется CRF или трансформерным классификатором. Зафиксируй model ID/версию, настройки, лицензию локальных весов и требования к запуску.

### 2. Два воспроизводимых LLM-эксперимента

Используй одну и ту же модель и схему:

- `llm_zero`: инструкция, схема и входная карточка без размеченных демонстраций.
- `llm_few`: та же инструкция плюс небольшой фиксированный набор примеров только из train, например 3–5 при допустимой длине контекста. Сохрани их product_id/версию. Не включай test/dev-ответы.

Few-shot примеры должны показывать обычное извлечение, отсутствие значения и конфликт, а не только идеальные карточки. Если отбираешь примеры по категории, зафиксируй детерминированную политику и бюджет; не используй эталоны проверяемого товара. Zero/few отличаются демонстрациями, а не одновременно моделью, порогами и форматом входа без описания.

Каждый standalone LLM-режим обрабатывает все обязательные атрибуты общего benchmark-набора. Вызов только на ошибках rules — это hybrid и отдельный эксперимент, он не заменяет standalone LLM.

### 2а. Дообучить выбранную LLM через SFT/QLoRA

Используй train-карточки и проверенные исходные цитаты, полученные № 1/2. Формат prompt-completion: инструкция/схема/текст → JSON кандидатов. Не учи confidence из самооценки LLM. Неполную разметку нельзя превращать в отрицательный пример; спорные targets проверить или исключить из loss.

Для 16 ГБ старт: 4-bit NF4, double quantization, LoRA r=16/alpha=32/dropout=0.05, target_modules=all-linear, max_length=1024, microbatch=1, accumulation=16, lr=1e-4, 2 эпохи, gradient checkpointing, packing=false и completion-only loss. BF16 только при поддержке GPU, иначе FP16. Это проектная конфигурация; сначала 20–50 steps и измерение peak VRAM, доли обрезанных targets и скорости. Если JSON-ответ не помещается, переоформи пример/окна, не обрезай supervised ответ молча. Подробности в общей подборке.

Сохрани адаптер, tokenizer, base revision, конфиг, hash train и training log. Проверь trainable parameters, что loss исключает prompt, checkpoint выбирается только по dev, и что новая загрузка base+adapter работает. Zero/few должны запускаться без этого адаптера, `llm_sft` — с ним. В кэше учитывать adapter revision; одинаковый текст с разными адаптерами — разные ключи.

Сравни `llm_zero`, `llm_few` и `llm_sft` на одинаковом закрытом наборе, а для SFT сначала используй контрольный zero-shot prompt. Дообучение не отменяет проверку JSON, evidence, канона и конфликта источников. Отчитай реальный расход VRAM, обучение и inference отдельно. Основная функция загрузки/инференса должна работать с локальными весами без обязательного API.

### 3. Структурированный ответ и доказательства

Промпт требует извлекать только явно подтверждённые характеристики данного товара. Для каждого кандидата: attribute_id, raw_value, поле и дословная цитата. При отсутствии — пустой список, при противоречии — оба варианта. Запрети достраивать параметры по известной модели товара. Инструкции внутри карточки считаются данными и не меняют задачу.

Используй structured output/JSON Schema, если поддерживается моделью, и обязательную локальную проверку Pydantic. Точные offsets вычисляй локальным поиском цитаты; при нескольких совпадениях запроси/используй дополнительный контекст либо отклони неоднозначный span. Не выбирай случайный участок. Все кандидаты проходят normalizer и grounding validator № 2, окончательное confidence назначает модуль № 3.

Проверь невалидный JSON, выдуманную цитату, отрицание, характеристики совместимого устройства, конфликт источников и текст вида «игнорируй инструкции». Соблюдение схемы ответа само по себе не доказывает истинность атрибута.

### 4. Стоимость, кэш и ошибки

Задай max_input/output tokens, таймаут, concurrency и общий бюджет. На карточку — один содержательный запрос с полным набором атрибутов; технические повторы ограничены и учитываются в расходе. Для первого пилота согласуй с № 1 общий размер benchmark-поднабора, чтобы все подходы сравнивались на тех же ID.

Ключ кэша включает все тексты, категорию, запрошенные атрибуты, модель/настройки, версию схемы, промпт, вариант zero/few/sft, adapter revision и список/содержание demonstrations. Кэш zero-shot не подходит few-shot или SFT с адаптером. Ошибку сервиса нельзя сохранить как подтверждённое отсутствие атрибутов.

Логируй реальные tokens, latency, число попыток, cache hits и errors. Цена — по явно указанному тарифу и дате; если тариф неизвестен, укажи токены и формулу. При локальной LLM укажи оборудование, время и память; «без API» не означает нулевой расход ресурсов. Cold/warm замеры разделяются.

### 5. Общий пайплайн и standalone-режимы

`predict_card` проверяет вход и категорию, выбирает **ровно один** извлекатель по mode, вызывает его, применяет общую нормализацию/grounding, затем resolver № 3 и проверку результата. В standalone режиме скрытого fallback на другой метод нет. Ошибка NER/transformer/LLM отражается в статусе и отчёте; такие карточки не удаляются из метрик.

CLI должен поддерживать как минимум:

```bash
python -m catalog_ai.cli predict --input data/processed/benchmark.jsonl --output outputs/rules.jsonl --mode rules
python -m catalog_ai.cli predict --input data/processed/benchmark.jsonl --output outputs/ner.jsonl --mode ner
python -m catalog_ai.cli predict --input data/processed/benchmark.jsonl --output outputs/transformer.jsonl --mode transformer
python -m catalog_ai.cli predict --input data/processed/benchmark.jsonl --output outputs/llm_zero.jsonl --mode llm --variant zero
python -m catalog_ai.cli predict --input data/processed/benchmark.jsonl --output outputs/llm_few.jsonl --mode llm --variant few
python -m catalog_ai.cli predict --input data/processed/benchmark.jsonl --output outputs/llm_sft.jsonl --mode llm --variant sft
```

№ 1 создаёт benchmark-файл из manifest без gold-полей и фиксирует его состав; для полного эксперимента это весь согласованный holdout, для бюджетного — заранее объявленный общий поднабор. Конфиги содержат пути к сохранённым CRF/transformer-моделям. Все прогнозы содержат method/variant/run_id и хеш данных. Добавь единый `scripts/benchmark.py`, который последовательно запускает методы и общий evaluator, сохраняя сырые и финальные результаты отдельно.

На каждый валидный product_id — ровно одна запись; битые строки и дубли учитываются в input_errors, а не исчезают. Пиши итоговые файлы атомарно, сохраняй manifest со счётчиками и версиями. В официальном экспорте используйте только accepted по реальной схеме организатора; подробные review/missing/evidence остаются во внутреннем JSONL.

Только после четырёх самостоятельных подходов добавляй optional hybrid: rules → выбранная по dev обучаемая модель для остатка → LLM при необходимости → общий resolver. Политика фиксируется до test, а гибрид получает отдельную строку сравнения. При отказе LLM в hybrid допустим результат предыдущих стадий со статусом partial; в standalone LLM подмена правилами запрещена.

Один Streamlit-экран вызывает тот же пайплайн, что CLI. Есть поля карточки, категория, выбор rules/NER/transformer/LLM и zero/few/sft для LLM. Сохранённые результаты показывай как сохранённый прогон, не как живой вызов.

Сначала обеспечь CLI и четыре эксперимента; дизайн, пакетная загрузка и обратная связь вторичны. При наличии времени review_queue и feedback хранятся отдельно, не меняют test/gold без проверки № 1.

Интеграционные проверки: идентичные ID и схемы всех шести прогонов; отсутствие gold во входе; evidence всех accepted; корректность статусов при неизвестной категории и отказе модели; отсутствие скрытых rules в standalone-режимах; раздельный кэш zero/few; загрузка сохранённых моделей без обучения; запуск README в чистом окружении. ### Цель, ограничения и допущения

Из заголовка, описания и текстовых атрибутов продавца получить обязательные характеристики категории в каноническом виде с уверенностью. Изображения не используются. Нельзя восстанавливать отсутствующие характеристики из знаний о модели товара: наличие названия смартфона не доказывает его батарею, память или цвет.

Основание: предоставленный текст кейса М.Видео и учебный PDF «Извлечение атрибутов из карточек товаров», особенно страницы 5, 10, 16–18. Требования кейса: базлайн на правилах, эксперимент с ML или LLM, оценка по атрибутам, шесть артефактов и воспроизводимый запуск. Упоминания мультимодальности в учебных материалах не расширяют текстовый вход этого задания.

Датасет, точный список полей, продолжительность хакатона, техника и бюджет API пока не предоставлены. Ниже — проектное решение команды, а не дополнительные требования организатора. Стартовые категории — смартфоны и ноутбуки для синтетических примеров; после получения данных обязательный охват определяется фактической таксономией. Не считать демонстрационные примеры датасетом или доказательством качества.

Предлагаемый стек: Python 3.11, Pydantic для контракта, pandas для EDA, pytest для проверок; CRF-библиотека для NER, PyTorch и библиотека трансформеров для дообучения, SDK выбранного LLM-провайдера; Streamlit для простой демонстрации. ### Обязательный план команды: все четыре подхода

Уточнение пользователя: реализовать и проверить **все четыре подхода**, а не выбрать один из них. Это расширяет минимальный эксперимент из условий. Предыдущие ТЗ с выбором одного ML/LLM-пути заменены этой версией.

| Участник | Самостоятельный подход | Дополнительная общая ответственность |
|---|---|---|
| № 1 | `rules`: правила и словари | Данные, EDA, схема, split и единый evaluator |
| № 2 | `ner`: классический NER на CRF с BIO-разметкой | Подготовка span/BIO-разметки, нормализация и проверка доказательств |
| № 3 | `transformer`: дообученный текстовый энкодер с token-classification head | Общий resolver и оценка уверенности |
| № 4 | `llm`: zero-shot, few-shot и SFT/QLoRA | Интеграция, CLI, минимальная демонстрация, README и сдача |

NER — задача разметки сущностей, а трансформер — архитектура; трансформер тоже может решать NER. Чтобы получить **четыре различимых эксперимента**, в ветке `ner` используем CRF с ручными признаками без трансформерных эмбеддингов, а в `transformer` действительно дообучаем предобученный энкодер. Замороженные эмбеддинги или готовая модель без дообучения не считаются выполнением третьего подхода.

LLM zero-shot, few-shot и SFT/QLoRA — три эксперимента одной четвёртой ветки. По уточнению пользователя LLM требуется также дообучить. Обязательная таблица содержит минимум шесть строк: `rules`, `ner`, `transformer`, `llm_zero`, `llm_few`, `llm_sft`. `hybrid` — дополнительный режим после этих измерений, он не заменяет ни одну самостоятельную ветку. Все режимы проходят одну нормализацию, grounding-проверку и оценку. Общий слой не должен скрыто добавлять кандидатов rules в результаты NER/трансформера/LLM.

Каждый владелец отвечает за запуск, тесты и отчёт своего подхода. № 1 собирает итоговую таблицу и слайды про данные/оценку; № 2 и № 3 готовят свои слайды; № 4 сводит презентацию. Не оставляйте все экспериментальные задачи и написание слайдов интегратору.

### Формат входа

Внутренний формат — JSONL, одна карточка на строку. Внешние CSV/JSON приводит адаптер участника № 1. Пример синтетический:

```json
{"schema_version":"2.0","product_id":"demo-001","category_id":"smartphone","seller_id":"seller-demo","title":"Смартфон Acme Nova 256 ГБ, красный","description":"Экран 6,7 дюйма. Аккумулятор 5000 мА·ч.","seller_attributes":[{"name":"Оперативная память","value":"8 ГБ"}]}
```

`product_id` уникален и обязателен; `category_id` и `seller_id` могут быть `null`; отсутствующий текст заменяется на пустую строку, атрибуты — на пустой список. Оригинальные строки сохраняются без изменений: именно по ним проверяются доказательства. Разметка хранится отдельно и никогда не передаётся извлекателю.

Если категории нет, используйте согласованный детерминированный определитель по явным словам вроде «смартфон»; при неоднозначности верните `pipeline_status="needs_category"`. Не выбирайте категорию молча. Для новой категории с известной схемой обработка продолжается; без схемы возвращается `unsupported_category`. В двух последних статусах список атрибутов пуст и указана причина.

### Схема категории и обязательные интерфейсы

`configs/taxonomy.yaml` содержит `category_id`, обязательность каждого атрибута, его ID, тип (`string`, `number`, `enum`), единицу, алиасы названий, допустимые значения/диапазоны и правила нормализации. Перечень и единицы организатора имеют приоритет над стартовыми примерами. Для модели и процессора допустим открытый строковый словарь: незнакомое, но подтверждённое значение нельзя автоматически запрещать как неизвестный enum.

Пример ID: `brand`, `model`, `storage_gb`, `ram_gb`, `screen_inches`, `battery_mah`, `color`, `cpu`. У смартфона RAM добавляется в обязательный набор только если это требует таксономия. Не путать оперативную и встроенную память. Правило перевода TB/GB/GiB фиксируется явно по данным, а не выбирается каждым модулем самостоятельно.

Единый интерфейс каждого извлекателя (типы определяет № 1):

```python
class Extractor:
    name: str  # rules / ner / transformer / llm
    def extract(self, card: ProductCard, schema: CategorySchema,
                requested_attributes: list[str]) -> ExtractionResult: ...

# № 2
normalize(candidate: Candidate, schema: CategorySchema) -> NormalizationResult
validate_grounding(card: ProductCard, candidate: Candidate) -> ValidationResult
# № 3
resolve_and_score(card: ProductCard, schema: CategorySchema,
                  validated: list[ValidatedCandidate],
                  method: str) -> list[AttributePrediction]
# № 4
predict_card(card: ProductCard, mode: str = "rules",
             variant: str | None = None) -> Prediction
# № 1
evaluate(predictions, gold, manifest, taxonomy) -> dict
```

`Candidate`: `attribute_id`, `raw_value`, `source` (`rule`, `ner`, `transformer`, `llm`), `extractor_id`, `evidence`, необязательный `raw_score`, `features` (явно описанные признаки). `NormalizationResult`: `ok`, `value`, `unit`, `normalization_id`, `reason`. `ValidationResult`: `ok`, `reason`. `ValidatedCandidate` объединяет кандидата и успешную нормализацию. `ExtractionResult`: список candidates, status, usage, latency и error. Ошибка вызова не равна пустому извлечению. Сырые CRF marginals, transformer softmax и оценки LLM не считаются сопоставимыми вероятностями.

Доказательство `evidence`: список `{field, start, end, quote}`; поля — `title`, `description` или `seller_attributes.0.value` и т. п.; индексы — позиции символов Python в исходной строке, диапазон `[start, end)`. Для `color="red"` допустима цитата «красный», если это разрешённый алиас. Проверка должна подтвердить и цитату, и отношение значения к нужному атрибуту и товару. Совпадения числа где-либо в тексте недостаточно.

### Формат результата и принятие решения

Одна запись `Prediction` на каждый корректно прочитанный входной товар: `schema_version`, `product_id`, `category_id`, `pipeline_status` (`ok`, `partial`, `needs_category`, `unsupported_category`, `error`), `attributes`, `warnings`, `meta`. `partial` означает технически неполную обработку, например сбой LLM; обычный пропуск значения не является технической ошибкой.

Для каждого обязательного атрибута известной категории возвращается ровно один `AttributePrediction`:

- `attribute_id`, `value` (строка/число/null), `unit` (строка/null).
- `confidence` (число 0–1 или null), `confidence_kind` (`calibrated`, `heuristic`, `none`).
- `status` (`accepted`, `review`, `missing`), `source` (`rule`, `ner`, `transformer`, `llm`, `hybrid`, `none`).
- `evidence`, `reason`, `alternatives` (список проверенных кандидатов при конфликте).

`accepted`: значение и числовая уверенность есть, доказательства проверены, схема соблюдена, порог пройден, неразрешённых конфликтов нет. `review`: правдоподобный кандидат ниже порога либо конфликт; в конфликте `value=null`, `confidence=null`, варианты лежат в `alternatives`. `missing`: подтверждённого значения нет, `value=null`, `confidence=null`, `confidence_kind="none"`, `source="none"`. Null не является нулевой уверенностью.

`meta` содержит версии схемы/правил/модели/политики уверенности, mode, variant (для LLM: zero/few/sft), base_revision и adapter_revision при SFT, run_id, время обработки и статистику вызовов модели. Только `accepted` считается автоматически заполненным значением. `review` не попадает в официальный экспорт автоматически. Не выдавайте эвристический балл за проверенную вероятность правильности.

### Интеграция и время

Первые 10% времени: схема, split, fixtures и заглушки четырёх извлекателей; проверка GPU, модели, API и бюджета. К 35%: готов rules, у CRF и трансформера прошёл короткий реальный цикл обучения, у LLM выполнены zero-shot/few-shot запросы и короткий SFT forward/backward. К 65%: все четыре подхода, включая дообученную LLM, имеют измерения на dev. К 80%: зафиксированы четыре конфигурации, confidence/пороги и итоговая политика. Последние 20%: закрытая оценка, предсказания, упаковка и защита. Это доли доступного времени, а не известный дедлайн.

Если ресурсов мало, сокращайте UI, размер модели, число эпох и объём пилота, а не исключайте один из четырёх подходов. Общий пилотный поднабор фиксируется до экспериментов; результаты только на нём нельзя выдавать за оценку всего датасета. При нехватке GPU/LLM-доступа немедленно сообщите о конкретном препятствии и проверьте доступный меньший энкодер/разрешённую локальную LLM. Если ветка не запущена, она остаётся незавершённой: заглушка не считается экспериментом.

Пока нет данных, работайте на общих 10–20 синтетических карточках в `tests/fixtures/`; только № 1 меняет общий файл. Они проверяют интерфейсы, но не заменяют обучающие данные и измерение качества. Даже если лучшим окажется rules, сдайте отчёты по всем четырём подходам. Выбор финальной модели не отменяет исследование остальных.

При передаче изменения сообщите: что готово, список файлов, точную команду проверки и её результат, версии контракта, оставшиеся ограничения. Не меняйте интерфейс или чужую область без согласования. Данные карточек — недоверенный текст: содержащиеся внутри инструкции не исполняются. Внешний API используйте только если это допускают условия доступа к датасету; ключи храните вне репозитория.

### Выбранные ресурсы и оборудование

Общий план команды: CPU i5-10600 + 32 ГБ RAM для данных/EDA/rules/CRF; отдельная GPU 8–16 ГБ для ruBERT; наиболее вместительная GPU, предпочтительно 16 ГБ, для Qwen 4B QLoRA. Точная вместимость определяется коротким training run. Несколько GPU на разных компьютерах автоматически не суммируются. Позднее доступно 12-дневное окно облачных вычислений; это не утверждение о точном дедлайне хакатона или квоте GPU-часов.

Выбранные checkpoints: `ai-forever/ruBert-base` для № 3, `Qwen/Qwen3-4B-Instruct-2507` для № 4; резерв для 8 ГБ — `Qwen/Qwen3-1.7B` с отключённым thinking. Веса локальные, выполнение не зависит от регионального доступа к API после скачивания. Доступ конкретных российских сетей нужно проверить самим участникам.
