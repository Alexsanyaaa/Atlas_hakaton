# Улучшение трансформера: версия 2

Дата: 17 октября 2026 года. Исходная модель — лучший checkpoint шага 20000 из полученного полного обучения. Оригинальные веса и исходные train/dev/test не изменены.

## Что выполнено

- Точно воспроизведены сохранённые метрики: TP 20119, FP 1263, FN 1195, support 21314, micro span F1 **0,942430**. Это оценка по silver-разметке, только по окнам с положительными метками; не качество готовой карточки.
- Сформирована очередь **1224 задач с расхождениями** (`error_tasks.jsonl`): 759 с пересечением ошибочных границ и 465 с лишними/пропущенными фрагментами. В 105 задачах также сработали признаки проблем разметки. Каждый случай требует проверки: расхождение с каталогом не равно ошибке модели.
- Создана отдельная версия silver-разметки по явным правилам схемы. Изменения затронули 3317 train и 396 dev записей. Из них 16 train и 3 dev записи исключены, потому что допустимых положительных меток не осталось. Это неизвестная разметка, не подтверждённое отсутствие.
- У всех изменений есть исходный текст, старые и новые границы, причина и источник. Файл `data/participant3_refined/label_changes.jsonl`. Проверено отсутствие пересечений group_id между train/dev; исходные группы сохранены. Файл test не открывался и не использовался.
- Добавлены **107 полностью размеченных синтетических задач** в train и **23 отдельные синтетические диагностические задачи**. Это разметка, составленная агентом, а не ручной эталон организатора. Восемь повторов в B/C — вес примеров, а не увеличение количества уникальных задач.
- Исправлен код подготовки: тип памяти и максимальная поддерживаемая память больше не попадают в объём установленной RAM. Добавлена поддержка явно подтверждённых отрицательных примеров. Пересечённый границей окна span игнорируется, а не превращается в O или частичный положительный ответ.
- Добавлены scheduler, warmup, настройка weight decay, смешивание дополнительного train, начальная оценка checkpoint и журнал learning rate. Сохранение старого лучшего checkpoint остаётся безопасным.

Например, цвет в коммерческом имени модели бывает спорным; такие изменения можно пересмотреть по журналу. Исправленный dev не является новым независимым gold. Сначала сравнивайте модели на одной версии разметки.

## Что показал маленький стресс-набор

В нём 23 задачи для пяти придуманных карточек, включая 14 задач с отсутствующими значениями, совместимость, отрицания, другие единицы и несколько цветов. Исходный checkpoint дал 8 ложных срабатываний на 14 отрицательных задачах. Строгий span F1 на всём наборе — 0,5143. При пороге 0,99 F1 составил 0,7619, но осталась одна лишняя извлечённая сущность.

Это **не падение каталожного F1 с 0,94**: набор намеренно другой, маленький и трудный. По нему нельзя оценить частоту ошибок во всём каталоге. Порог 0,99 не подбирался как рабочий по этому набору; это один из заранее заданных диагностических срезов. Файл `baseline_challenge/metrics.json` содержит полный результат. Набор не входит в обучение и не используется скриптом для выбора checkpoint. Он уже открыт в ходе диагностики, поэтому не является закрытым итоговым тестом.

## Пороги

Условно разделили использованный dev по group_id на две части: подбор и диагностическую проверку. Исходный checkpoint ранее выбирался по всему этому dev, поэтому вторая часть **не независимый тест**. Порог применяется к минимуму токенных вероятностей span; это не вероятность правильности карточки.

| Режим предварительного отбора | Порог | Precision на диагностической части silver | Recall | F1 |
|---|---:|---:|---:|---:|
| Баланс F1 | 0,5831 | 0,9599 | 0,9333 | 0,9464 |
| Максимальный охват при нижней границе precision ≥0,95 на части подбора | 0,5308 | 0,9501 | 0,9385 | 0,9443 |
| Максимальный охват при нижней границе precision ≥0,98 на части подбора | 0,9036 | 0,9826 | 0,8801 | 0,9285 |

Нижняя граница — Wilson 95%; это описательная оценка на silver, не гарантия работы в продакшене. Она не учитывает зависимость нескольких фрагментов одного товара. Режим 95% может быть мягче баланса F1, поскольку цель — максимальный охват при выполненном ограничении точности. В `diagnostics.json` есть полный перебор и предварительные показатели по атрибутам.

Политики `balanced_review.yaml`, `precision95_review.yaml`, `precision98_review.yaml` готовы для **экспериментальной фильтрации/очереди проверки**, у всех `auto_accept: false`, калибраторы пустые. При отсутствии достаточного support порог не объявляется найденным. Эти числа относятся к исходному checkpoint и исходной silver-разметке; после нового обучения нужно подобрать их заново. Для вероятностной калибровки и автоприёма нужны проверенные человеком случаи, включая отсутствие характеристик, с отдельными группами для calibration/tuning/evaluation. Не выдавать 98% из таблицы за обещанную точность автоприёма.

## Четыре конфигурации

| Вариант | Начальные веса | Данные | Learning rate | План |
|---|---|---|---:|---|
| A | Лучший полученный checkpoint, шаг 20000 | Исправленный train, выборка до 32000 записей | 2e-5, постоянный | До 2000 новых optimizer steps |
| B | Тот же checkpoint | Как A + 107 сложных задач с весом 8 | 2e-5, постоянный | До 2000 шагов |
| C | Тот же checkpoint | Как B | 1e-5, linear decay, warmup 6% | До 2000 шагов |
| D | Исходный ai-forever/ruBert-base | Весь исправленный train + сложные задачи с весом 12 | 2e-5, linear decay, warmup 6% | До 3 эпох; ограничение 6 часов |

A/B/C используют один seed, одинаковый базовый sampler и один dev. A→B проверяет влияние сложных примеров; B→C — совместное изменение LR и scheduler, а не эффект каждого параметра отдельно. В A/B/C исходные веса уже видели старую шумную разметку; это новое дообучение весов с новым optimizer, не точное возобновление старой сессии. D позволяет проверить обучение без прежнего шума, но одновременно меняет бюджет данных/обучения, поэтому не изолирует один фактор.

Batch 8, accumulation 3: эффективный batch до 24. Длина 256, stride 64, FP16, gradient checkpointing. A/B/C оцениваются до начала и каждые 500 шагов; patience 3. D — каждые 1000. Остановки по шагам/времени и ранняя остановка могут сократить запуск. Лучшая начальная модель сохранится, если дообучение ухудшит dev F1. Результатов GPU A/B/C/D пока нет: параметры — кандидаты для сравнения, не найденный оптимум.

Начать практично с C; чтобы оценить вклад данных и настройки, затем выполнить A и B. D — более дорогая контрольная проверка. Все запуски последовательные, каждый пишет новую папку. Для сравнения нескольких seed нужны дополнительные запуски; один seed не измеряет устойчивость.

Схемы scheduler: [официальная документация Transformers](https://huggingface.co/docs/transformers/main_classes/optimizer_schedules).

## Проверки

49 автоматических тестов прошли, включая новые проверки отрицательных окон, пересечённых spans, исправлений RAM/модели/CPU, целостности синтетических границ и совпадающих confidence. Короткий CPU-запуск на маленьком encoder прошёл 2 шага с scheduler, дополнительными отрицательными примерами, оценкой до обучения, сохранением и повторной загрузкой checkpoint. Это проверка исполнения, не результат улучшения ruBERT-base. Реальный полученный ruBERT-base проверен инференсом на стресс-наборе. В текущей среде нет GPU; полноценное сравнение A/B/C/D следует выполнить на RX 9070 XT.
